- **日期**：2026-08-22

- **前置**：燃料計硬體已上機驗收通過（`docs/power-module-purchase.md §10.8`）

## 1. 背景

燃料計硬體 2026-08-22 驗收通過：I2C `0x36` 在線、讀數 3.844V 對比電表 3.88V（差 36mV）、SOC 54.4%。但**主韌體目前完全讀不到它**——開機不偵測 `0x36`，只有獨立環境 `fuel-gauge-check` 讀得到。

本 spec 涵蓋從「主韌體讀得到」到「SoT 規定的電量顯示行為全部到位」。

### 1.1 SoT 相關條文

| 條文 | 要求 |
|---|---|
| §13.16 | 執行中低電量顯示一次「低電量／建議接上行動電源」，之後只閃爍圖示，**不播放提示音** |
| §13.17 | 右上角顯示電量圖示；充電中顯示 `🔋⚡`；低電量時圖示閃爍 |
| §19.1 | 系統設定選單含「電池資訊」項 |
| §19.7 | 裝置資訊畫面顯示「電池：86%」「充電狀態：充電中」 |
| §20.3 | 案件進行中不強制關機，只提醒；低電量仍允許開始 OHCA／通氣，但需警告「是否開始？」 |

### 1.2 規格缺口（本 spec 補上的決策）

SoT **沒有**定義下列任何一項，以下數值為本 spec 拍板：

- 低電量門檻（無任何百分比或電壓數值）
- 電量圖示的形式（只寫「電量圖示」，未規定四格）
- 取樣頻率與趨勢判定方式

> 📌 `power-module-purchase.md §10.6` 的 checklist 引用了 memory「四格電量圖示規格來源」，但該 memory 不存在——「四格」是工程端推測，非 PM 規格。本 spec 採四格呈現，但這是設計決定而非規格遵循。

## 2. 硬體約束

### 2.1 沒有充電狀態訊號

MAX17043 只提供電壓（VCELL）與電量（SOC），**沒有充電狀態暫存器**；聯騰一體板也未拉出 CHRG/STDBY 腳（`power-module-purchase.md §10.5`）。

**決策：以軟體趨勢推導充電狀態**，不飛線改硬體。理由是零硬體改動、純邏輯可 native test，且 §10.6 已記載此方向。代價是有延遲且需設死區，見 §3.3。

### 2.2 I2C bus 現況

`gpio-allocation.md §5.4`「當前 I2C bus 位址表」：GPIO 42=SDA / 41=SCL，bus 上有 `0x36` 燃料計、`0x57` EEPROM、`0x68` DS3231，實測無衝突。

## 3. 讀取層

### 3.1 lib 結構

比照既有 `firmware/lib/ems_rtc/` 的 backend + Null 降級 pattern：

```
firmware/lib/ems_fuel_gauge/
  ems_fuel_gauge.h          FuelGaugeBackend 純虛介面 + FuelReading struct
  max17043_backend.{h,cpp}  I2C 0x36 實作（唯一碰硬體的檔案）
  null_fuel_gauge.h         不在線降級，回 valid=false（不可命名 null_backend.h——與
                            ems_rtc/null_backend.h basename 相同會讓 include 撈錯檔）
  fuel_gauge_logic.{h,cpp}  純邏輯：換算／趨勢推導／低電量判定
```

`fuel_gauge_logic` 獨立的理由：換算公式、趨勢狀態機、遲滯判定全部不需硬體，可 native test。對齊既有教訓「硬體相依檔案內的算式要搬進 pure-logic lib」。

### 3.2 main.cpp 掛載

比照 `firmware/src/main.cpp` `STEP 06.5` 的 RTC 三分支：偵測到 `0x36` 掛 `Max17043Backend`，否則掛 `NullFuelGauge`。缺硬體不 crash、不阻擋開機。

### 3.3 暫存器換算（沿用已驗證公式）

來源 `power-module-purchase.md §10.8`，勿重推：

```
VCELL (0x02)：12-bit A/D，資料在 bits 15:4
    mV = (raw >> 4) * 1.25          // MAX17043 為 1.25mV/LSB
SOC (0x04)：高位元組 = 整數 %，低位元組 = 1/256 %
    percent = (raw >> 8) + (raw & 0xFF) / 256.0
```

> ⚠️ MAX17048/49 的 VCELL 解析度是 78.125µV/LSB，換型號沿用本公式會差 16 倍。

### 3.4 拍板數值

| 項目 | 值 | 理由 |
|---|---|---|
| 取樣間隔 | **10 秒** | 電量變化極慢，高頻取樣無益 |
| 趨勢判定窗 | **30 秒**（3 個取樣點） | 插上 USB 後約半分鐘顯示「充電中」；更短會被雜訊騙，更長使用者覺得沒反應 |
| **趨勢輸入來源** | **VCELL（mV）**，非 SOC（%） | 見 §3.4.1 |
| 趨勢死區 | **±3mV**（約 2.4 LSB） | 30 秒窗最小訊號 5mV（500mA 充電），死區須小於它才偵測得到；又須大於靜置雜訊。**此值為推導初值，需上機實測校正**，見 §10 |
| 低電量門檻 | **進入 20% ／ 解除 25%** | 遲滯必要——單一門檻會在邊界反覆觸發提示與閃爍。20% 對 1000mAh 約留 200mAh |

> 低電量門檻仍以 **SOC(%)** 判定，只有「趨勢推導」改用 VCELL。兩者用途不同：門檻要的是絕對電量，趨勢要的是變化方向。

#### 3.4.1 為何趨勢輸入改用 VCELL（2026-08-22 修訂）

原設計用 SOC(%) 做趨勢推導，經 Task 2 的 review（三個面向獨立判定 Critical）發現該設計**雙向失效**：

| 情境 | 期望 | 原設計實際結果 |
|---|---|---|
| 電池靜置，SOC 在 53/54/55 間抖動 | Idle | Charging / Discharging 反覆閃爍（**誤報**） |
| USB-C 500mA 充電中 | Charging | 30 秒窗僅變 0.42%，量化後 delta=0 → Idle（**漏報**） |

根因同一個：`push()` 的輸入是 `uint8_t` 百分比，delta 必為整數，死區 `0.5` 等價於「delta ≥ 1」——它只濾得掉 delta=0，濾不掉 ±1 的地板抖動；而真實充電訊號在 30 秒窗內又小於 1 個量化單位。**訊號比雜訊還小，調整死區數值無法同時解決兩個方向。**

改用 VCELL 後的訊號尺度（1.25mV/LSB）：

| 充電電流 | 30 秒窗變化 | 對應 LSB |
|---|---|---|
| USB-C host 500mA（SoT §20.4 峰值上限） | 5.0 mV | 4.0 |
| TP4056 預設 1A | 10.0 mV | 8.0 |

對照原 SOC 方案的 30 秒窗變化 = 0 LSB。VCELL 讓訊號脫離量化底噪，死區才有可設定的空間。

附帶好處：不依賴 MAX17043 的 ModelGauge 演算法，而該演算法在低電量區的精度**尚未驗證**（見 §10）。

### 3.5 充電狀態列舉

```cpp
enum class ChargeState : uint8_t { Unknown = 0, Charging, Discharging, Idle };
```

**`Unknown` 是誠實的初始態**：開機後前 30 秒趨勢窗未滿，無法判斷充放電，此時充電符號不顯示——不是顯示「未充電」，那是猜的。

## 4. 顯示層

### 4.1 統一重繪出口

現況：`main.cpp` 有 20+ 處 `drawXxx(); display.pushSprite(0, 0); return;` 各自為政，沒有統一出口。要讓電量圖示出現在所有畫面，必須先收斂。

**改為 `presentFrame()`**，內部依序：畫全域 overlay（電量圖示）→ `pushSprite(0, 0)`。所有呼叫點改成 `drawXxx(); presentFrame(); return;`。

效益：電量圖示只寫一次；未來任何全域 overlay 只加一處；新畫面作者不會漏。

### 4.2 圖示位置：獨立頂行

既有 `OHCA_BADGE_Y = 14` 那一行：中央是標題（`drawCenteredText`），右側是通氣／Training overlay（三者都錨在 `SCREEN_W - 8, OHCA_BADGE_Y + 2`）。上方 y=0~13 這 14px 是空的。

**電量圖示放 y≈2 的絕對右上角**，不進 y=14 那行。

```
  y=2   →              [▓▓░]   ← 電量，~10px 高
  y=14  →    已鎖定      通氣 3  ← 既有，座標完全不動
```

理由：零向後相容風險（不動任何已驗收版面）、所有畫面位置統一。代價是頂部只有 14px，圖示做到約 10px 高（手機狀態列的比例）。

### 4.3 圖示形式

- 四格電池外框，依 SOC 填格。分界為 **0~24% = 1 格 ／ 25~49% = 2 格 ／ 50~74% = 3 格 ／ 75~100% = 4 格**；SOC 為 0 時仍畫 1 格空框（外框本身表示「有讀到值」）
- 充電中：外框內加閃電符號（對應 SoT §13.17 的 `🔋⚡`）
- 低電量：整個圖示 1Hz 閃爍（500ms 翻轉）
- 燃料計不在線（`batteryPercent == 255`）：**完全不畫圖示**，連外框都不畫——畫空電池會被讀成沒電

### 4.4 DisplaySnapshot 新增欄位

`firmware/lib/ems_display_snapshot/ems_display_snapshot.h`：

```cpp
uint8_t batteryPercent;      ///< 0~100；255 = 燃料計不在線
uint8_t batteryChargeState;  ///< ems::ChargeState 列舉值
```

低電量閃爍相位走 `flags` 新增一個 bit，不另開欄位。

> ⚠️ **DisplaySnapshot 漏欄位已連踩 4 次**（historyCursor / summarySubmenuCursor / endCheckCursor / Phase G 設定選單）。新增欄位必須跑既有 5 步驟 checklist，確認 `DisplaySnapshotInputs`、比較函式、寫入點全部同步。

**`255` 當「不在線」哨兵，不用 0**：0% 是合法讀數（真的沒電），拿它兼作「讀不到」會讓硬體故障偽裝成電池耗盡。

**轉譯只能有一個出口**：`FuelReading`（`valid` 旗標）→ `batteryPercent`（`255` 哨兵）的轉換一律走
`ems::to_display_percent()`，哨兵常數 `ems::BATTERY_PERCENT_ABSENT` 與它同檔（`fuel_gauge_logic.h`）。
呼叫端不得自己 inline 寫 `valid ? percent : 255`——目的地是裸 `uint8_t`，漏判 `valid` 時
`NullFuelGauge` 回的 `percent = 0` 落在合法 `0~100` 內，沒有任何邊界檢查攔得住，畫面會把硬體故障
顯示成「電池耗盡」，正是本節要避免的那件事。守衛加在共用層，不是加在每個 caller 的記憶力上。

### 4.5 閃爍的副作用

低電量時畫面每 500ms 全片重繪。全片 `pushSprite` DMA 約 4ms @80MHz，量級可接受，但**低電量時反而更耗電**——這是 SoT 要求閃爍的必然代價。

局部 push 可省，但需另設計髒區域追蹤。**先做整片，實測有問題再優化**，不預先複雜化。

## 5. 低電量行為

| 規格 | 觸發條件 | 行為 |
|---|---|---|
| §13.16 | 案件進行中首次跨過 20% | 顯示一次「低電量／建議接上行動電源」，**3 秒**後自動消，**不發聲**，之後只閃圖示 |
| §20.3 | 低電量狀態下按 OHCA 入口 | 確認框「低電量／建議接上行動電源／是否開始？」，選「是」進案；選「否」**回主選單，不建立案件** |

**「案件進行中」的定義**：`globalState` 處於 OHCA 或獨立通氣流程，**Training 模式一併適用**（Training 也會耗電，救護員在練習時同樣需要知道電池狀況）。純選單瀏覽不觸發，避免在待機時跳提示。

§20.3 的確認框**複用既有 `SUBSTATE_AMIO_CONFIRM` / `drawAmioConfirmPrompt()` 的 pattern**，不另造輪子。Training 入口是否也要這道確認框，依上述定義為**要**——但 Training 是練習情境，若實作時覺得干擾過度，此為可回頭調整的點。

「顯示一次」的範圍是 **per-boot，不寫 NVS**：充完電拔掉再掉到 20% 應重新提醒；寫 NVS 會讓它一輩子只提醒一次。跨過門檻的判定以「上一次取樣在門檻上、這次在門檻下」為準，避免開機當下就已低電量時漏觸發——開機首次取樣即低於 20% 也算一次跨越。

## 7. 測試策略

**native（涵蓋全部純邏輯）**

- 換算：用實測黃金值 `0xC030` → 3843.75mV（`uint16_t` 取整捨去為 **3843**）、`0x366A` → 54.41%（取整捨去為 **54**）。文件他處出現的 3.844V / 54.4% 是四捨五入後的顯示值，非函式契約值——兩者不可混用
- 趨勢狀態機：上升／下降／持平／死區內不跳動／窗未滿回 `Unknown`
- **趨勢索引鑑別力**：測試數列必須能區分正確索引與 off-by-one。嚴格單調的數列（如 50,52,54）做不到——中間樣本永遠站在正確方向，選錯索引只讓 delta 變小不變號。必須有一組**非單調**數列（如 `3800 → 3900 → 3800`，正確為 Idle；誤讀中間值會判 Charging）
- **死區邊界**：須測到最小觸發值與死區內值的分界，否則死區常數被誤改也沒有測試會 fail
- **哨兵轉譯雙向**：`to_display_percent()` 兩個方向都要測——`valid=false` 且 `percent` 帶合法值（如 77）
  時必須回 `255`（證明只看 `valid` 不看 `percent`）；`valid=true` 且 `percent=0` 時必須回 `0`（證明
  合法的「真的沒電」不會被誤轉成哨兵）。只測其中一向，拿掉 `valid` 判斷的實作照樣全綠
- 遲滯：20% 進入、25% 解除，在 20~25% 之間來回不重複觸發
- 一次性提示：per-boot 只觸發一次
- 哨兵：`255` 不被當成 0%

**on-target**

- 燃料計不在線時掛 Null backend、開機不 crash
- 實機低電量閃爍目視確認

## 10. 已知限制

- 充電狀態有 30 秒延遲，開機前 30 秒為 `Unknown`
- 燃料計低電量區（接近 3.0V）精度**尚未驗證**——只在 3.84V 中段比對過電表，而那正是低電量警告最需要準的區間（`power-module-purchase.md §10.8`「未驗證項目」）。W3 實作前建議補驗，否則 20% 門檻的實際觸發點可能偏移
- 趨勢推導無法區分「充電中」與「USB 供電但電池已充飽」——兩者都會呈現 Idle 或微幅波動
- **死區 ±3mV 是推導初值，未經實測校正**。它的下界由訊號決定（500mA 充電 30 秒窗 5mV，死區須明顯小於此值），上界由靜置雜訊決定——而**靜置時 VCELL 的抖動幅度我們沒有數據**。目前唯一的觀測是 2026-08-22 驗收時 `fuel-gauge-check` 連跑 6 輪（12 秒）VCELL raw 恆為 `0xC030` 無抖動，但當時為 USB 供電且觀察窗過短，不足以推論靜置行為。Task 6 主韌體整合後應收一段長時間的靜置讀數，據以校正此值
- **趨勢推導層不對輸入做合理性檢查**：單筆 I2C 垃圾讀值會被當成真實變化，可能造成假的充放電判定（垃圾值落在窗口端點時尤其明顯）。不可信讀值的判定屬 `FuelReading.valid` 層（§3.1）的職責，該層完成前此缺口存在
- `ChargeTrendTracker` **本身沒有時間概念**，只認推入次數。「30 秒觀察窗」的成立完全依賴呼叫端維持 10 秒輪詢；若 Task 6 改變輪詢間隔，須回頭同步本 spec 與該類別的註解
